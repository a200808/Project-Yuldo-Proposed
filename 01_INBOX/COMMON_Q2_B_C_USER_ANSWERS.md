# COMMON Q2 — 사용자 답변 및 미반영 결정 기록

Status: [PROPOSED]
Record Type: User-provided decisions awaiting cross-domain review and formal Canon integration
Owner: YULDO-AI-GENERAL
Source: Project Yuldo GENERAL planning conversation, 2026-10
Canon Notice: 이 문서는 사용자가 대화에서 제시한 답변을 보존하기 위한 기록이다. 개별 항목의 Confirmed 승격이나 기존 Canon 수정은 별도 검토·통합 절차를 거친다. 이미 Confirmed인 내용과 충돌하면 기존 Canon을 유지하고 충돌을 표시한다.

## 1. 기록 목적 및 상태

이 문서는 공통 질문지 2번의 B(세계관 규칙과 경계), C(상태와 변화)에 대한 사용자의 답변 중 공식 저장소에서 확인되지 않은 내용을 보존한다.

- [USER DECISION] 사용자가 방향을 명시적으로 선택한 내용
- [OPEN] 구체적인 규칙·수치·예외가 아직 결정되지 않은 내용
- [REVIEW] 다른 영역 또는 기존 Canon과의 정합성 검토가 필요한 내용

이 기록만으로 공식 Canon이 변경되지는 않는다.

## 2. B. 세계관 규칙과 경계

### B-1. 규칙 분류 원칙

- [USER DECISION] 전제·법칙·예외·금지사항의 분류는 필요할 때 사용한다.
- [USER DECISION] 모든 규칙에 네 가지 분류를 억지로 모두 붙이지 않는다.
- [USER DECISION] 별도의 '알려진 오해' 항목을 의무화하지 않는다. 오해 가능성이나 보충 설명은 해당 규칙에 포함한다.

### B-2. 현대 시설의 이동, 크로노스의 초기 상태 및 자원 확보

- [USER DECISION] 현대 기술·소모품은 초기에 보유한 물량을 소모하며 운용한다. 소모품을 모두 사용하면 대체품을 확보하기 전까지 해당 기술·무기의 사용에 차질이 생긴다.
- [USER DECISION] 조선에서 확보하는 대체품은 원래 현대 소모품과 완전히 동일하지 않으며 성능이나 운용에 제약이 있다.
- [USER DECISION] 중반 이후에는 현대 기술을 조선식으로 재해석하거나 현대 무기를 개조해 운용하는 방향으로 전환한다.
- [OPEN] 초반 보유량, 소모 속도, 대체품의 성능 차이, 기술 전환 시점과 단계는 미결정이다.

### B-3. 도술의 범위와 작동 원칙

- [USER DECISION] 도술은 장비·무기에 부여하는 인첸트와 유사한 강화 기능을 가진다.
- [USER DECISION] 도술은 인첸트에 한정되지 않고 별도의 공격·이동 등 전투 기술도 가능하다.
- [USER DECISION] 비전투 분야의 도술 활용은 현재 기획 범위에서 제외한다.
- [USER DECISION] 도술 사용자는 홍길동과 일부 특수 인물로 제한한다.
- [USER DECISION] 도술은 생체 전자기적 힘에 가까운 성격을 가진다.
- [USER DECISION] 크로노스는 현대 기술력으로 도술을 부분적으로 모방하거나 방해할 수 있다.
- [USER DECISION] 도술은 현대 물리 법칙을 전반적으로 따르며 에너지 소모라는 제약이 있다.
- [USER DECISION] 축지(공간 접기)는 허구적 세계관 전제로 허용한다. 이를 실제 물리학에서 검증된 현상으로 설명하지 않는다.
- [USER DECISION] 사망자 부활, 무에서 물질 창조, 시간 조작은 불가능하다.
- [USER DECISION] 영혼에 접근하는 행위는 무당이 아닌 인물에게 허용하지 않는다.
- [USER DECISION] 크로노스는 장거리 도술 이동을 방해하는 장치를 운용한다. 해당 장치가 작동하는 동안 플레이어의 장거리 이동은 제한되며, 장치를 제거해야 해당 지역으로 이동할 수 있다.
- [OPEN] 도술 에너지의 원천·회복·소모량, 기술별 범위·지속·실패 조건, 생체 전자기적 힘의 정확한 의미, 크로노스 방해기의 범위·작동 조건·해제 방식, 무당의 영혼 접근 한계는 미결정이다.
- [DEFERRED] 평행세계와 기억 복제는 현재 게임 방향과 맞지 않아 보류한다.

### B-4. 역사·미스터리 원칙

- [USER DECISION] 게임은 엄격한 역사 고증을 목표로 하는 작품이 아니라 대체 역사물이다.
- [USER DECISION] 큰 시대 배경과 조선의 기본 체제는 역사적 기반을 유지한다.
- [USER DECISION] 인트로와 주요 배경은 역사적 사실을 중심으로 검토하되, 그 외의 세부 창작은 게임 재미와 개연성을 기준으로 허용한다.
- [USER DECISION] 세계의 현상은 개발진 내부적으로 설명 가능한 구조를 갖춰야 한다. 다만 플레이어에게 그 설명을 공개하지 않고 미스터리로 남길 수 있다.
- [OPEN] 고증 검증이 필요한 핵심 역사 범위, 창작 자유의 세부 경계, 플레이어에게 공개할 정보의 범위는 미결정이다.

### B-5. 기존 Confirmed와의 정합성 주의

공식 CORE_CANON은 연구시설의 이동, 크로노스의 자원 확보, 희귀 광물, 귀환 연료 부족, 한양 방향 확장 등 일부 큰 방향만 정의한다. 이 문서의 상세 답변은 기존 Confirmed를 대체하지 않는다.

- [REVIEW] 사용자는 크로노스가 한양 방향으로 진격하는 동기에 광물 확보뿐 아니라 조선의 정치·행정 중심지를 장악하고 기존 권력구조를 통제하려는 목적도 있다고 설명했다. 현재 확인한 CORE_CANON에는 이 동기가 구체적으로 기록되어 있지 않으므로 WORLD/NPC_FACTIONS 검토 후 별도 반영이 필요하다.
- [OPEN] 시설 이동 경계, 이동 인원·물자·장비의 정확한 규모, 귀환 메커니즘, 광물의 세부 물성·분포, 수탈 체계 등은 기존 문서의 미결정 항목으로 유지한다.

## 3. C. 상태와 변화

### C-1. 공통 상태 추적 범위

- [USER DECISION] 공통 상태 범주는 다음 8개를 유지한다: 플레이어, 퀘스트, 지역, 세력, 동료, 자원, 장비, 스토리.
- [USER DECISION] 현재 범주를 추가하지 않되, 필요하면 향후 확장할 수 있다.

### C-2. 상태 정의 소유권

- [USER DECISION] GENERAL은 공통 상태 목록, 전체 구조, 영역 소유권 및 문서 관계를 조정한다.
- [USER DECISION] 전문 AI는 담당 영역의 구체적인 상태 값, 범위, 초기값, 변경 조건, 지속성을 정의한다.
- [USER DECISION] REVIEW는 영역 간 충돌·누락·중복을 검토한다.

### C-3. 상태 지속성 분류

- [USER DECISION] 상태 지속성은 영구 상태, 임무 한정 상태, 반복 콘텐츠 상태, 임시 상태로 구분한다.
- [USER DECISION] 이 분류는 폐쇄형이 아니며 향후 확장 가능하다.

### C-4. 하나의 사건으로 여러 상태가 변경되는 경우

- [USER DECISION] 상황에 따라 혼합 방식을 사용한다.
- [USER DECISION] 강하게 연결된 상태 변경은 하나의 묶음으로 처리한다. 묶음의 핵심 변경 중 하나라도 실패하면 전체 묶음을 취소하거나 재처리한다.
- [USER DECISION] 서로 독립적인 상태 변경은 개별 성공·실패를 허용할 수 있다.
- [OPEN] 원자적 묶음의 경계, 의존 관계, 처리 순서, 재시도 및 보상 처리 규칙은 전문 시스템 설계에서 정의한다.

### C-5. 상태 변경 기록 수준

- [USER DECISION] 개발 단계에서는 상세한 상태 변경 기록을 사용한다.
- [USER DECISION] 배포 단계에서는 기록을 요약·축약하는 방향을 검토한다.
- [OPEN] 사용자가 언급한 '양자화'의 구체적 의미와 적용 대상은 미결정이다. 이를 게임 상태 데이터 자체의 손실 변환으로 해석하지 않는다.
- [PROPOSED] 상세 진단 로그와 배포용 요약 기록을 분리한다.

### C-6. 상태 변경 기록 보존

- [USER DECISION] 기록 등급에 따라 보존 기간을 차등 적용한다.
- [USER DECISION] 핵심 스토리·퀘스트·지역 상태 변경은 장기 보존한다.
- [USER DECISION] 일반 NPC 반응, 임시 자원 변화 등은 기간 제한 또는 요약을 허용한다.
- [OPEN] 보존 기간, 삭제 주기, 기록 등급 기준은 미결정이다.

### C-7. 상태 변경 기록의 사용처

- [USER DECISION] 상태 변경 이력은 개발·디버깅 전용으로 사용한다.
- [USER DECISION] 게임플레이 시스템이 진단용 이력 로그를 직접 참조하지 않게 한다.
- [USER DECISION] 실제 게임 진행을 결정하는 현재 상태 데이터와 진단용 이력 로그를 분리한다.

### C-8. 내부 상태와 저장 데이터

- [USER DECISION] 내부 게임 상태 데이터와 저장 파일의 구조를 분리한다.
- [USER DECISION] 저장 시 내부 상태를 저장 데이터 구조로 변환·검증한 뒤 기록한다.
- [USER DECISION] 불러오기 시 저장 데이터를 검증한 뒤 현재 내부 상태 구조로 변환한다.

### C-9. 저장 데이터 버전 호환

- [USER DECISION] 자동 변환을 기본으로 하되 변환할 수 없는 데이터는 별도 복구·안내 절차를 제공하는 혼합 방식을 사용한다.
- [USER DECISION] 기존 진행 상황과 자산을 최대한 유사하게 보존한다.
- [USER DECISION] 변환 과정에서 데이터를 임의 삭제하거나 대체하지 않는다.
- [OPEN] 변환 불가 데이터 처리, 백업·롤백 정책은 저장 시스템 설계에서 구체화한다.

### C-10. 백업 정책

- [USER DECISION] 복수 시점의 백업을 보관한다.
- [USER DECISION] 데이터 손상 또는 변환 실패 시 이전 정상 백업으로 복구할 수 있어야 한다.
- [OPEN] 백업 개수, 보존 기간, 자동 생성 시점은 미결정이다.

### C-11. 저장 시점

- [USER DECISION] 자동 저장을 중심으로 하되 수동 저장도 허용한다.
- [USER DECISION] 플레이어가 매번 저장을 의식하지 않아도 진행이 보존되는 경험을 목표로 한다.
- [OPEN] 저장 주기와 트리거는 미결정이다.

### C-12. 진행 슬롯과 사망 처리

- [USER DECISION] 단일 진행 슬롯을 사용한다.
- [USER DECISION] 사망했다고 직전 저장 파일로 롤백하는 방식은 사용하지 않는다.
- [USER DECISION] 사망 처리는 저장 롤백과 분리한다.
- [USER DECISION] 백업은 기술적 오류·손상 대응용이며 사망 전 상태로 되돌리는 세이브 로드 기능이 아니다.

### C-13. 데이터 삭제

- [USER DECISION] 게임 내 삭제 기능은 허용하되 강한 확인 절차를 둔다.
- [USER DECISION] 플레이어가 PC 저장 폴더에서 외부 삭제하는 것도 허용한다.
- [USER DECISION] 의도적 삭제와 기술적 손상을 구분한다.
- [USER DECISION] 백업 자동 복구가 플레이어의 의도적 삭제를 무효화하지 않도록 한다.

### C-14/C-15. 클라우드 저장·동기화

- [USER DECISION — LATEST] 초기 개발 및 초기 출시 범위에서는 로컬 저장만 기준으로 한다.
- [USER DECISION — LATEST] 자체 클라우드 동기화와 클라우드 백업은 초기 범위에서 제외하고 추후 검토한다.
- [USER DECISION — LATEST] 플랫폼 자체 클라우드 기능도 나중에 검토한다.
- [USER DECISION — LATEST] 향후 확장 가능성은 고려하되 현재 구조를 불필요하게 복잡하게 만들지 않는다.
- 이 결정은 이전에 논의된 로컬+클라우드 동기화 방향을 대체하는 최신 사용자 결정이다.

### C-17. 백업 위치

- [USER DECISION] 원본 저장 데이터와 백업은 별도 폴더에 보관한다.
- [USER DECISION] 기본 백업 위치는 원본과 같은 드라이브의 다른 폴더로 한다.
- [USER DECISION] 최초 실행 또는 저장 시스템 초기 설정 시 플레이어가 백업 위치를 선택하도록 한다.
- [USER DECISION] 플레이어는 원하는 다른 폴더나 드라이브를 지정할 수 있고, 설정에서 백업 위치를 변경할 수 있어야 한다.
- [USER DECISION] 백업 위치 접근 불가 또는 저장 공간 부족 시 오류를 안내한다.
- [OPEN] 외장 저장 장치 활용과 같은 드라이브 전체 고장에 대비하는 정책은 추후 검토한다.

### C-18. 백업 생성 시점

- [USER DECISION] 일반 저장 시 백업을 갱신한다.
- [USER DECISION] 메인 퀘스트 완료, 지역 해방, 주요 보스 처치, 중요한 스토리 분기 등 주요 사건에서는 별도의 보존용 백업을 생성한다.
- [OPEN] 보존용 백업의 개수와 보존 기간은 미결정이다.

### C-19. 백업 복구 방식

- [USER DECISION] 정상 백업이 명확하면 자동 복구를 우선 시도한다.
- [USER DECISION] 후보가 여러 개이거나 자동 복구에 실패하면 플레이어에게 선택권을 제공한다.
- [USER DECISION] 최근 백업이라는 이유만으로 최선의 복구 후보로 간주하지 않는다. 무결성, 버전, 생성 시각 등을 고려한다.

### C-20. 복구 동의와 거부

- [USER DECISION] 복구 전에 예상되는 진행 상황 손실을 안내하고 플레이어의 명시적 동의를 받는다.
- [USER DECISION] 동의하지 않으면 자동 복구를 진행하지 않는다.
- [USER DECISION] 복구 거부를 이유로 데이터 초기화나 강제 복구를 하지 않는다.
- [USER DECISION] 게임 진행이 불가능하면 복구 선택 화면에서 대기하고, 플레이어가 나중에 다시 선택할 수 있게 한다.
- [USER DECISION] 복구 후보, 백업 버전·생성 시각, 안내 버전, 동의·거부, 복구 결과를 기록하는 방안을 채택 방향으로 둔다.
- [USER DECISION] 복구 보류, 백업 선택, 백업 파일 내보내기를 지원하는 방향으로 한다. 내보내기는 원본 백업을 변경하지 않는다.
- [OPEN] 복구 안내 및 동의 기록의 정확한 형식·보존 기간은 미결정이다. 동의 기록이 모든 법적 분쟁을 방지한다고 보장하지 않는다.

### C-21. 복구 동의 범위

- [USER DECISION] 일반 복구는 작업 단위로 한 번 동의받는다.
- [USER DECISION] 복구 도중 최초 안내와 다른 손실이나 위험이 발견되면 중단하고 재동의를 받는다.
- [USER DECISION] 재동의가 없으면 복구를 진행하지 않는다.
- [USER DECISION] 복구 과정에서도 기존 원본과 백업을 가능한 한 보존한다.

### C-22. 무결성 검사

- [USER DECISION] 게임 실행 시 기존 저장 데이터를 검사한다.
- [USER DECISION] 저장 직후 생성된 데이터도 검사한다.
- [USER DECISION] 새 저장 기록의 검증 성공 후에만 백업 정리 작업을 수행한다.
- [USER DECISION] 새 저장 검증 성공만으로 기존 백업 전체를 삭제하지 않는다.
- [USER DECISION] 최소한의 정상 복구 지점과 주요 사건 백업을 보존한다.

### C-23. 백업 개수·용량 관리

- [USER DECISION] 일반 백업은 최대 개수 제한을 두고 오래된 순서로 정리한다.
- [USER DECISION] 주요 사건 백업은 별도 보존 규칙을 적용하고 일반 정리 대상에서 제외한다.
- [USER DECISION] 전체 백업 용량에도 상한을 둔다.
- [USER DECISION] 최소 하나 이상의 정상 복구 지점을 유지한다.
- [OPEN] 구체적인 개수와 용량 상한은 개발 단계에서 결정한다.

### C-24. 저장 공간 부족 시 정리

- [USER DECISION] 저장 공간이 부족하면 백업을 먼저 검사한다.
- [USER DECISION] 손상되었거나 사용할 수 없는 백업을 우선 삭제한다.
- [USER DECISION] 그래도 공간이 부족해 정상 백업을 삭제해야 한다면, 오래된 정상 백업을 삭제하기 전에 플레이어에게 공간 확보 여부를 묻는다.
- [USER DECISION] 플레이어가 동의하면 오래된 순으로 정리한다.
- [USER DECISION] 플레이어가 거부하면 정상 백업을 삭제하지 않고 공간 부족을 안내한다.
- [USER DECISION] 반복 확인을 줄이기 위해 '다음엔 묻지 않기' 옵션을 제공하고, 해당 선택은 설정에서 언제든 변경할 수 있게 한다.
- [USER DECISION] 주요 사건 백업과 최소 정상 복구 지점은 일반 정리 정책으로 삭제하지 않는다.

### C-25. 저장 파일 조작과 불법 복제 방지

- [USER DECISION] 플레이어가 자신의 로컬 저장 데이터를 조작하는 행위는 허용한다.
- [USER DECISION] 방지 대상은 불법 복제, 무단 라이선스 사용, 무단 실행이다.
- [USER DECISION] 저장 파일 암호화를 불법 복제 방지의 핵심 수단으로 취급하지 않는다.
- [PROPOSED] 불법 복제 방지는 게임 실행·배포 보안 영역에서 다룬다. 플랫폼 구매·라이선스 확인, 실행 시 인증, 게임 파일 무결성 검사, 변조된 실행 파일 탐지, 필요 시 DRM을 검토한다.
- [USER DECISION] 초기 PC 출시 및 개발의 우선 기준 플랫폼은 Steam이다.
- [OPEN] 오프라인 실행 허용 범위, DRM 적용 수준, Steam 외 PC 스토어 지원 여부는 미결정이다.
- [REVIEW] Steamworks 및 플랫폼 라이선스 기능과 게임 핵심 시스템을 분리해 향후 다른 스토어로 확장할 때의 종속성을 줄일 필요가 있다.

## 4. D. 규칙 충돌과 예외 처리 — 사용자 답변

### D-1. 규칙 충돌 시 우선순위
- [USER DECISION] 공통 규칙의 우선순위는 **세계관 규칙 > 스토리·퀘스트 진행 규칙 > 게임플레이 규칙** 순서로 둔다.
- [PROPOSED] 게임플레이 규칙은 세계관상 불가능한 행동을 허용하지 않는다.
- [PROPOSED] 스토리·퀘스트 진행 규칙은 세계관 규칙을 위반할 수 없다.
- [PROPOSED] 스토리·퀘스트 진행과 게임플레이가 충돌하면 스토리·퀘스트 진행 규칙을 우선한다.
- [OPEN] 이 우선순위 아래에서 의도된 게임플레이 예외를 어떤 승인·표시·구현 절차로 허용할지는 미결정이다.

### D-2. 세계관 규칙에 명시되지 않은 예외적 행동·현상
- [USER DECISION] 기존 규칙에 명시되지 않은 예외적 행동이나 현상은 임시로 허용할 수 있으나, REVIEW 검토를 거쳐 정식 규칙으로 편입할지 결정한다.
- [PROPOSED] 임시 허용은 기존 Confirmed 규칙을 자동 변경하거나 예외를 Canon으로 승격하는 행위가 아니다.
- [PROPOSED] REVIEW는 기존 세계관 원칙과의 정합성, 다른 영역에 미치는 영향, 악용 가능성, 시스템·콘텐츠 비용을 검토한다.
- [PROPOSED] 검토 결과에 따라 별도 예외로 문서화하거나, 규칙 개정 제안으로 남기거나, 임시 허용을 철회한다.
- [OPEN] 긴급 임시 허용의 승인 주체, 적용 범위·기간, 플레이어에게 노출할지 여부, 정식 규칙 편입 승인 절차는 미결정이다.

### D-3. 임시 허용의 유효 기간
- [USER DECISION] 임시 허용은 REVIEW 검토가 완료될 때까지 유지한다.
- [USER DECISION] REVIEW는 기획 단계에서 수행하는 검수 과정이며, 별도의 사후 승인 단계로 취급하지 않는다.
- [PROPOSED] REVIEW 결과에 따라 예외를 정식 규칙에 반영할지, 수정할지, 철회할지 결정한다.
- [PROPOSED] REVIEW 검토가 완료되면 해당 예외의 임시 허용 상태를 해소한다. 임시 허용을 검토 완료 이후까지 자동 연장하지 않는다.




### D-4. 기존 규칙에 없는 상황의 규칙화
- [USER DECISION] 기존 세계관 규칙에 명시되지 않은 상황이 발생하면, 세계관 규칙보다 하위 위계에 속하는 규칙이라도 우선 새로 만들어 둔다.
- [PROPOSED] 규칙의 위계가 낮다는 이유로 필요한 하위 규칙의 작성을 미루거나, 규칙이 없다는 이유만으로 상황을 무규칙 상태로 방치하지 않는다.


### D-5. 새 하위 규칙의 작성·확정 시점
- [USER DECISION] 새로운 규칙의 필요성이 발견되는 즉시 임시 규칙으로 작성한다.
- [USER DECISION] 해당 규칙과 관련된 기획을 진행할 때 임시 규칙을 검토하고 확정한다.
- [PROPOSED] 발견 단계에서는 규칙을 누락하지 않도록 임시 상태로 먼저 기록하고, 관련 기획 단계에서 상위 규칙과의 정합성 및 영향 범위를 검토해 확정 여부를 정한다.


### D-6. 상위 규칙과 하위 규칙의 충돌 처리
- [USER DECISION] 기본 원칙은 상위 규칙을 유지하고 충돌하는 하위 규칙을 수정하는 것이다.
- [USER DECISION] 다만 하위 규칙이 매우 중요하거나 상위 규칙에 허점·불완전성이 있는 경우에는 상위 규칙의 개정도 고려한다.
- [USER DECISION] 규칙 간 충돌 처리 구조를 실제 입법 체계의 위계·개정 절차를 참고해 설계한다.
- [PROPOSED] 하위 규칙의 중요성이나 상위 규칙의 허점이 확인되었다고 상위 규칙을 자동 변경하지 않는다. 충돌 사례와 영향 범위를 검토하고, 필요한 경우 상위 규칙 개정안을 별도 Proposed로 제시한다.
- [PROPOSED] 상위 규칙 개정은 해당 상위 규칙의 기존 적용 범위, 다른 하위 규칙, 세계관·스토리·게임플레이에 미치는 파급효과를 함께 검토한 뒤 사용자 결정으로 확정한다.


### D-7. 상위 규칙 개정의 선행 조건
- [USER DECISION] 개정 전에 대상 규칙보다 상위에 있는 규칙을 모두 확인한다.
- [USER DECISION] 개정안이 확인된 모든 상위 규칙과 충돌하지 않을 때만 개정할 수 있다.
- [USER DECISION] 대상 규칙보다 상위 규칙이 존재하지 않는 경우에도 개정을 검토할 수 있다.
- [PROPOSED] 상위 규칙 확인이 끝나지 않았거나 개정안이 상위 규칙과 충돌하면 개정을 보류하고, 개정안 또는 하위 규칙을 수정한다.

### D-8. 규칙 개정안 형식
- [USER REQUEST] 규칙 개정안의 표준 형식을 정한다.
- [PROPOSED] 개정안에는 다음 항목을 기록한다: (1) 개정안 ID·제목, (2) 상태, (3) 대상 규칙 ID·문서 경로·위계, (4) 현행 문구, (5) 문제와 개정 사유, (6) 개정 제안 문구, (7) 상위 규칙 목록과 충돌 검증 근거, (8) 하위·연관 규칙 및 영역별 영향, (9) 대안과 비교, (10) REVIEW 결과와 미해결 쟁점, (11) 사용자 결정, (12) 승인일·적용 버전·후속 문서 갱신 목록.
- [PROPOSED] 개정 전후 문구를 비교 가능하게 제시하고 변경 이유와 검증 근거를 추적 가능하게 남긴다.
- [USER DECISION] 규칙 개정안 표준 형식은 상위 규칙과 하위 규칙을 포함한 모든 규칙 개정에 공통 적용한다.


### D-9. 규칙 개정안 이력 보존
- [USER DECISION] 최종 확정된 규칙 개정안은 보존한다.
- [USER DECISION] 그 외 개정 과정의 이력은 필요하다고 판단되는 경우에만 요약본으로 보존한다.
- [PROPOSED] 모든 중간 초안·검토 기록을 일률적으로 보존하지 않는다. 향후 규칙 해석, 결정 근거 추적, 반복 방지 또는 프로젝트 운영에 필요하다고 판단되는 이력만 간결한 요약으로 남긴다.


### D-10. 개정안 승인 전 효력
- [USER DECISION] 규칙 개정안이 사용자 승인되기 전까지는 기존 규칙을 유지한다.
- [USER DECISION] 개정안 승인 전 임시 적용이 필요한 경우에는 정식 개정 절차와 구분되는 별도 절차로 다룬다.
- [PROPOSED] 개정안 작성·검토·REVIEW 완료만으로 기존 규칙의 효력은 바뀌지 않는다. 임시 적용은 별도 근거와 범위·기간·해제 조건을 정해 관리하며, 사용자 승인 없이 기존 규칙을 대체하지 않는다.
