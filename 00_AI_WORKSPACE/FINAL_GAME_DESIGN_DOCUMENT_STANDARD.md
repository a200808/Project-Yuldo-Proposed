# 최종 통합 게임 기획서 기준

상태: [PROPOSED]

## 1. 목적

프로젝트 율도의 모든 개별 기획 문서를 최종적으로 하나의 통합 게임 기획 문서로 연결한다.

이 문서는 단순한 요약본이나 소개서가 아니다.

**게임을 처음 접하는 개발자, 기획자, 아티스트, 레벨 디자이너, 시나리오 담당자, QA, 외부 협력자가 문서를 읽었을 때 가능한 한 동일한 게임을 머릿속에 그릴 수 있도록 만드는 상세 설계 기준**이다.

최종 목표는 다음과 같다.

> 문서를 충분히 읽은 두 사람이 같은 상황을 상상하고, 같은 규칙을 이해하며, 같은 결과를 예상할 수 있어야 한다.

## 2. 최종 기획서의 성격

최종 통합 기획서는 다음 네 가지를 동시에 만족해야 한다.

1. **플레이어 경험 명세**
   - 플레이어가 무엇을 보고
   - 무엇을 듣고
   - 무엇을 선택하고
   - 무엇을 조작하고
   - 어떤 피드백을 받고
   - 어떤 결과를 경험하는지 설명한다.

2. **게임 시스템 명세**
   - 시스템의 목적
   - 입력
   - 상태
   - 처리 규칙
   - 결과
   - 예외
   - 다른 시스템과의 연결을 설명한다.

3. **콘텐츠 명세**
   - 스토리
   - 캐릭터
   - 지역
   - 퀘스트
   - 적
   - 무기
   - 장비
   - 동료
   - 이벤트 등 실제 게임에 존재하는 콘텐츠를 정의한다.

4. **세계관 및 논리 명세**
   - 왜 그런 시스템과 콘텐츠가 존재하는지
   - 세계관 내부에서 어떻게 설명되는지
   - 어떤 것은 가능하고 어떤 것은 불가능한지 정의한다.

## 3. 상세화 원칙

분량을 인위적으로 제한하지 않는다.

다만 장황함 자체를 목표로 하지 않는다.

필요한 경우 다음 수준까지 상세화한다.

- 정의
- 목적
- 전제조건
- 정상 흐름
- 입력
- 처리
- 출력
- 상태 변화
- 예외 상황
- 실패 조건
- 성공 조건
- UI/UX 피드백
- 사운드/연출
- 다른 시스템과의 연결
- 플레이어가 알 수 있는 정보
- 플레이어가 알 수 없는 정보
- NPC가 아는 정보
- 세계관상 가능한 범위
- 금지되는 행동
- 데이터 간 의존관계

## 4. 플레이어 경험을 기준으로 설명

모든 핵심 시스템은 가능하면 다음 질문에 답해야 한다.

### 플레이 전

- 플레이어는 무엇을 알고 있는가?
- 무엇을 모르는가?
- 어떤 목표를 가지고 있는가?

### 행동 중

- 플레이어가 무엇을 입력하는가?
- 게임은 어떻게 반응하는가?
- 어떤 시각/청각/문자 피드백이 발생하는가?
- 플레이어가 다음 행동을 어떻게 판단하는가?

### 결과

- 성공하면 무엇이 바뀌는가?
- 실패하면 무엇이 바뀌는가?
- 세계 상태가 어떻게 변하는가?
- 퀘스트/스토리/장비/세력 등에 어떤 영향이 있는가?

### 반복

- 이 행동을 왜 다시 하는가?
- 반복할 때 무엇이 달라지는가?
- 장기적으로 어떤 성장 또는 변화가 발생하는가?

## 5. 시스템 로직 작성 기준

핵심 시스템은 설명만 하지 않는다.

예:

`A를 사용한다 → 조건 B를 검사한다 → B가 참이면 C → B가 거짓이면 D`

처럼 상태와 결과의 관계를 명확하게 표현한다.

필요하면 다음 형식을 사용한다.

- 입력
- 조건
- 처리
- 결과
- 상태 변화
- 예외
- 우선순위
- 시스템 간 이벤트 전달

숫자가 확정되지 않은 경우 숫자를 임의로 만들지 않고 구조와 의존관계부터 기록한다.

## 6. 플레이어가 느끼는 것과 내부 로직을 분리

같은 기능을 두 관점에서 기록할 수 있다.

### Player View

플레이어가 실제로 경험하는 것.

### System Logic

게임 내부에서 발생하는 상태 변화와 판정.

두 관점이 서로 모순되지 않아야 한다.

## 7. 예외 상황을 중요하게 취급

완성 단계에서는 정상적인 플레이만 설명해서는 안 된다.

다음도 가능한 한 정의한다.

- 사용 불가능한 상태
- 조건 미충족
- 플레이어의 잘못된 입력
- 퀘스트 순서가 예상과 달라진 경우
- 특정 NPC가 사망/부재한 경우
- 지역 상태가 변화한 경우
- 장비가 없는 경우
- 이동 경로가 차단된 경우
- 적이 점령한 경우
- 시스템 간 우선순위가 충돌하는 경우

## 8. 동일한 게임을 상상하게 하기 위한 용어 규칙

핵심 용어는 하나의 공식 정의를 가진다.

같은 대상을 여러 이름으로 부르지 않는다.

예:
- 공식 명칭
- 별칭
- 플레이어에게 표시되는 명칭
- NPC가 사용하는 명칭
- 내부 시스템 명칭

이 차이가 필요한 경우 각각의 사용 조건을 명시한다.

## 9. 문서 간 중복과 충돌

최종 통합 단계에서는 개별 문서를 단순히 이어 붙이지 않는다.

다음 작업을 수행한다.

- 중복 내용 통합
- 서로 다른 정의 탐지
- 용어 통일
- 상호참조 정리
- 설정 충돌 해결 또는 명시적 보류
- 시스템 의존관계 정리
- 누락된 연결 발견
- 동일 규칙의 다중 정의 제거

하나의 공식 규칙은 가능한 한 하나의 원본 정의를 갖는다.

## 10. 최종 문서의 예상 범위

최종 기획서는 최소한 다음 영역을 포함한다.

1. 프로젝트 개요

11. 플레이어 시스템
12. 이동 및 축지
13. 전투
14. 도술
15. 적 시스템
16. 무기

실제 범위는 기획이 진행되면서 확장될 수 있다.

## 11. 최종 통합의 원칙

최종 통합은 다음 순서를 따른다.

`개별 문서 → 영역별 정리 → 영역 간 연결 → 충돌 검수 → 누락 검수 → 용어 통일 → 시스템 로직 정리 → 플레이어 경험 검수 → 통합 기획서`

통합 과정에서 새 설정을 임의로 추가하지 않는다.

새로운 설정이 필요하다면 별도의 Proposed로 분리하고 사용자 승인을 거친 뒤 반영한다.

## 12. Canon과 최종 기획서의 관계

최종 기획서도 Source of Truth의 승인 절차를 따른다.

통합 기획서에 적혀 있다는 이유만으로 새로운 내용이 Canon이 되는 것이 아니다.

최종 문서 작성 시점에도 다음 상태를 구분한다.

- [CONFIRMED]
- [PROPOSED]
- [REVIEW]
- [UNDECIDED]

최종 출시용 기획서는 승인된 내용을 중심으로 구성하며, 미결정 사항은 별도로 명시한다.

## 13. 완성 기준

최종 기획서가 충분히 완성되었다고 판단하려면 다음 질문에 답할 수 있어야 한다.

- 처음 플레이하는 사람의 첫 30분은 어떻게 진행되는가?
- 플레이어는 무엇을 보고 무엇을 조작하는가?
- 각 핵심 시스템은 어떤 조건에서 작동하는가?
- 시스템 간 충돌이 발생하면 어떤 규칙이 우선하는가?
- 플레이어의 행동이 월드에 어떤 변화를 만드는가?
- 퀘스트와 스토리가 게임플레이와 어떻게 연결되는가?
- 장비와 성장의 모든 핵심 규칙은 무엇인가?
- 실패하면 정확히 무엇이 발생하는가?
- 예외 상황에서는 어떻게 처리되는가?
- 주요 콘텐츠가 어디에서 어떤 이유로 등장하는가?
- 다른 사람이 문서를 읽고 동일한 게임을 설계할 수 있는가?

마지막 질문이 핵심 완료 기준이다.

## 14. 최종 기획서의 목적

최종 기획서는 개발자에게 단순히 "무엇을 만들 것인가"를 알려주는 문서가 아니다.

**"그것이 실제 게임 안에서 어떻게 존재하고, 플레이어가 어떻게 경험하며, 어떤 규칙으로 작동하는가"를 재현할 수 있게 하는 문서**다.

따라서 최종 기획서의 품질은 페이지 수가 아니라 **재현 가능성, 일관성, 완결성, 추적 가능성**으로 판단한다.
